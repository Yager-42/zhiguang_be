## 1. 背景与目标

### 1.1 背景

zhiguang 是一个 **AI 辅助的内容社区后端**：以 `knowpost`（知识帖）为核心内容，已具备发布流水线、关注关系（relation）、推荐 / 关注 feed（recommendation）、评论（comment）、点赞收藏计数（counter）等能力。**目前没有任何商业化 / 支付 / 广告模块**，纯内容社区。

团队已拥有一个**现成的竞价系统**，其核心能力为：给定一批候选 + 各自出价，按某种拍卖机制选出赢家、排序并（可选）结算。

本 PRD 定义：**如何将该竞价能力接入 zhiguang，在不破坏内容生态的前提下产生商业与激励价值。**

### 1.2 核心思路

竞价系统的本质是**"稀缺资源的多方竞争性分配器"**。因此接入点不是"找一个叫拍卖的场景塞进去"，而是：

> 把 zhiguang 里所有"从一批候选中选少数几个、当前用固定规则（先到先得 / 纯算法排序 / 硬限流）分配"的决策点找出来，将选择逻辑替换为"调用竞价系统"。

### 1.3 目标

1. 建立内容社区的**轻量变现能力**（流量位 / 咨询档期竞价）。
2. 建立**知识付费与激励闭环**（悬赏问答、付费咨询）。
3. 最大程度复用现有模块（profile / knowpost / comment / counter / relation / llm / search / storage），最小化新增依赖。

### 1.4 非目标（本期不做）

- 接入第三方 RTB（DSP / SSP / 广告交易台）——本期只做**第一方**竞价。
- 完整的广告创意管理 / 投放后台 / DMP。
- 真实支付网关对接与完整金融合规体系——本期优先用**虚拟货币 / 质量分**跑通内循环；真金白银为后续阶段（见 §8）。

## 2. 角色与场景

| 角色 | 说明 | 在本方案中的诉求 |
|---|---|---|
| 内容消费者 | 浏览 feed 的普通用户 | 看到高质量、少打扰的内容 |
| 创作者 | 发布 knowpost 的用户 | 争取更多曝光；提供咨询变现 |
| 专家 / 认证创作者 | 标记为可提供咨询的高质量创作者 | 出售档期 / 知识变现 |
| 提问者 | 悬赏方 | 花钱买到真正解决问题的答案 |
| 回答者 | 投标方 | 用能力赚取赏金，不被白嫖 |
| 平台 | escrow 托管方 + 仲裁方 | 维护生态健康，抽取合理费用 |

## 3. 功能需求

接入分三类资源，对应两种拍卖方向。

| 功能 | 被竞价的稀缺资源 | 拍卖方向 | 竞争方 | winner 规则 |
|---|---|---|---|---|
| 3.1 套餐流量位 | feed 排序权重 / 置顶 / search / 粉丝触达 | 正向 | 创作者（买方） | max(bid) |
| 3.2 付费咨询 | 专家档期 | 正向 | 用户（买方） | max(bid) |
| 3.3 悬赏问答 | 赏金 / 回答权 | 逆向（招投标） | 回答者（卖方） | max(综合标分) / min(报价) |

> **工程前提**：竞价系统需支持两种 winner 模式——**正向（最高价赢）** 与 **逆向（最优标赢）**。套餐与咨询共享正向实现；悬赏走逆向。

### 3.1 套餐流量位竞价（正向拍卖）

将四类曝光资源归并为统一的**「曝光套餐」**：

- **推荐位权重**：mixed home feed 中 `final_score = relevance_score + λ · bid`，把出价叠加到 recommendation 现有相关性分上（注意防过度商业化，见 §7）。
- **置顶位**：承接现有 `KnowPostTopPatch`，从手动指定改为竞价分配。
- **search 置顶**：搜索结果商业位。
- **粉丝触达优先级**：follow-feed fanout 在收件箱容量受限时，按竞价决定哪些内容优先触达。

机制：GSP 二价（业界标准、易解释）；创作者以虚拟货币 / 质量分出价买权重。

### 3.2 付费咨询（正向拍卖）

- 专家档期作为稀缺资源，用户竞价抢热门时段。
- 与套餐**完全同构**，复用正向拍卖实现，仅把"被竞价资源"从曝光位换成档期。
- 复用 `profile`（专家标记）+ `relation`（关注）。

### 3.3 悬赏问答（逆向拍卖 / 招投标）

知识付费的核心，与 `knowpost`（提问）+ `comment`（回答）+ `counter`（认可度）语义高度咬合。

**产品流程（状态机，高层）：**

```
[发布悬赏] 提问者出价 + 托管赏金(可撤回)
     │  LLM 准入：判断"此问题是否值得悬赏"(LLM 自己答得好则劝退)
     ▼
[投标]   多个回答者投标：历史战绩 + 领域 + 粗方向（不含解题步骤）
     │  系统自动算 [合法性审查 + 领域匹配分 + 历史资质分] → 投标质量分
     ▼
[评标]   提问者基于投标质量分 + 综合判断选中标者
     ▼
[锁定]   提问者锁定赏金（不可撤回）        ← 白嫖窗口在此关闭
     ▼
[交付]   中标者交付完整答案（可分阶段里程碑）
     ▼
[结算]   提问者确认 → 放款 / 不满意 → 仲裁(扣质押)
```

详细信任与防白嫖机制见 §4（本 PRD 的核心设计）。

## 4. 关键设计：悬赏的信任与防白嫖

悬赏的成败取决于能否同时满足两个看似矛盾的需求：

- **甲方（提问者）**：在不看到方案的前提下，判断乙方（回答者）真能解决我的问题；
- **乙方（回答者）**：我的方案 / 劳动成果不会被甲方窃取。

设计原则：**不追求在投标阶段 100% 确定对方能力（这不现实），而是提供足够强的能力信号 + 出了问题有退路。**

借鉴真实招投标制度，并将"法律兜底"系统性替换为「经济约束 + 平台规则 + 技术存证」。

### 4.1 双向保护机制对照

| 风险 | 保护方 | 真实招投标机制 | zhiguang 落地 |
|---|---|---|---|
| 乙方没能力 / 答不好 | 提问者 | 资质预审 + 投标保证金 | 历史战绩 + 系统匹配分 + **投标质押** |
| 乙方中标后跑单 | 提问者 | 投标保证金没收 | 质押没收 + 信用扣分 |
| 甲方窃取方案 | 回答者 | NDA + IP 登记 + 比稿费 | **比稿补偿池** + 平台条款 + **时间戳存证** |
| 甲方看了不付 | 回答者 | 预付款 + 履约保函 | **托管 + 锁定不可撤回 + 里程碑** |
| 双方耍赖 | 双方 | 第三方招投标中心 / 仲裁 | **平台做 escrow + 仲裁方** |

### 4.2 三道核心防线（防"提纲被 LLM 补全后白嫖"）

**防线一：定位——悬赏只服务"LLM 答不了"的问题（信息层让白嫖不可行）**

> 若一个问题的提纲就能让 LLM 跑出不错的结果，那它本身不稀缺，不该存在为悬赏。

发布时由 LLM 自评能力边界：LLM 若能答好，则劝退悬赏。甜区锁定在需**私有数据 / 领域经验 / 交互诊断 / 定制交付**的问题。

**防线二：隔离——"能力证明"与"答案内容"分开（砍掉危险中间层）**

- 投标只交：历史战绩 + 领域 + **粗方向**（不含具体解题步骤）。
- 详细解题内容**只在赏金锁定后**交付。
- 投标阶段暴露的内容公开、安全、喂给 LLM 也补不出当前答案。

**防线三：制度——锁定前置，关闭白嫖窗口（改变激励）**

- 看完整答案前必须**锁定赏金（不可撤回）**。
- 配合 **比稿补偿池**：提问者发布时除主赏金外，预付小额补偿池，按投标质量分给所有投标者（哪怕未中标）——消除提问者"看了不采纳"的套利空间，同时激励回答者认真投标。

### 4.3 LLM 在流程中的定位（关键澄清）

LLM **不是**最终裁决者，而是**多重信号中"必要不充分"的一环**：

- ✅ **能做、应做**（流程前端，自动）：
  - 发布准入：判断问题是否值得悬赏（LLM 自评能力边界）。
  - 投标粗筛：合法性审查（逻辑自洽、答所问、不跑题）+ 领域匹配分。
- ❌ **不做**（不可逆决策）：
  - 不单独裁决"谁中标、谁拿钱"。

理由：
1. 合法性审查管"形式有效"，不管"实质能否解决"——二者有 gap。
2. LLM 审查可靠性 ∝ 其对该领域的能力；而悬赏恰好发生在它能力不足的领域，故审查本身也打折。
3. LLM 无 skin in the game（评错零成本），不能承担不可逆关键决策。

最终信任落回：**资质预审（看历史）+ 经济机制（质押 / 托管 / 锁定 / 仲裁 / 比稿池）+ 技术存证（时间戳）**。

### 4.4 存证

投标方案与最终答案提交时，平台用 `storage` 存**带时间戳的内容哈希**（可选上链），作为"我先有此内容"的事后举证依据，用于判罚甲方抄袭。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 套餐 / 咨询为**请求级实时**竞价（每次 feed / 咨询请求拍卖），须低延迟，复用 `cache`；悬赏为**状态机型**，无强实时要求。 |
| 安全 | 防刷单、防操纵评分、防洗钱（真金白银阶段）、资金安全（托管账户）。 |
| 公平 | 拍卖机制须可解释（GSP）；防出价操纵 / 串标。 |
| 合规 | 真金白银阶段需考虑支付牌照、资金存管、税务。 |
| 体验 | 内容消费侧广告位有频控 / 占比上限，避免过度商业化伤害留存。 |

---

## 6. 依赖与约束

- **复用**：`profile`、`knowpost`、`comment`、`counter`、`relation`、`llm`、`search`、`storage`、`cache`、`id`。
- **最大新增（瓶颈）**：**钱包 / 账户 + 托管状态机**。这是悬赏与真金白银套餐能否落地的真正瓶颈，**非竞价本身**。
- **竞价系统改造**：需支持正向（max bid）与逆向（最优标）两种 winner 模式。
- **货币**：本期默认虚拟货币 / 质量分（内循环，零合规成本）；真金白银为后续阶段。

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 支付 / 托管体系缺失 | 悬赏、真金白银套餐无法落地 | 先用虚拟货币跑通；钱包作为独立前置里程碑 |
| 过早广告化伤留存 | 用户流失 | 广告位频控 / 占比上限；优先内循环（创作者买流量）而非外部广告主 |
| LLM 审查被话术操纵（Goodhart） | 投标质量分失真 | 仅作粗筛信号，不单独裁决；叠加历史资质 + 经济约束 |
| 悬赏冷启动无回答者 | 功能空转 | 比稿补偿池激励；早期平台补贴 |
| 拍卖机制选择争议 | GSP vs VCG | 默认 GSP，文档说明取舍 |

## 8. 里程碑建议（按依赖复杂度排序）

| 里程碑 | 内容 | 依赖 | 备注 |
|---|---|---|---|
| **M1** | 套餐流量位竞价（虚拟货币） | 现有模块 + 竞价系统正向模式 | 最轻，先验证竞价系统接通；内循环不碰支付 |
| **M2** | 钱包 / 账户 + 托管状态机（最小版） | 新建 | 整个方案的瓶颈前置；M3 前必须完成 |
| **M3** | 悬赏问答（含 §4 全套机制） | M2 + 竞价系统逆向模式 | 语义最贴合知识社区，价值最高 |
| **M4** | 付费咨询 | M2（正向模式已在 M1） | 复用 M1 正向实现 + M2 钱包 |
| **M5** | 真金白银支付 / 合规 | M2 扩展 | 引入支付网关、合规、存管 |

> 注：若团队判断"知识付费"优先级高于"流量变现"，可对调 M1 与 M3（M2 钱包仍需前置）。

## 9. 未决决策（需评审拍板）

以下问题决定架构走向，需在进入 OpenSpec 前明确：

1. **出价货币**：虚拟货币 / 质量分（内循环，可立即跑）还是 真金白银（需支付合规）？影响是否必须先做 M2/M5。
2. **竞价频率**：套餐实时（每次请求拍卖）还是排期级（按天 / 时段）？决定延迟与架构复杂度。
3. **优先级**：先做套餐流量变现，还是先做悬赏知识付费？
4. **支付体系方案**：自建钱包还是接入第三方支付？真金白银阶段的存管 / 合规方案。
5. **拍卖机制**：GSP（二价）确认作为默认？
6. **抽取比例**：平台从套餐 / 咨询 / 悬赏中的抽成规则。
