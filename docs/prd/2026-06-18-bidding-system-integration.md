> **v0.1 → v0.2 主要变更**（来自评审 grilling）：
> - 套餐拆为「位竞价（GSP）」与「付费加权（非拍卖）」两类；GSP 仅适用位竞价（feed 权重叠加不是拍卖）。
> - 悬赏定为「招投标（人工定标）」而非逆向拍卖；竞价系统**逆向模式仅用于算投标质量分（参考）**，不自动定标。
> - 删除「比稿补偿池」（锁定前置已覆盖白嫖窗口），改用 **锁定前置 + 投标质押 + 平台补贴**。
> - 删除悬赏「不满意→仲裁」分支，改为**无争议结算**（超时自动放款 / 跑单退款+没收质押）+ 评价/信誉作软威慑。
> - 咨询不再称「完全同构套餐」，明确为**位竞价选人 + P2P 托管结算**；补 profile 专家标记 + 档期前置。
> - 出价货币定为**虚拟货币（封闭内循环）**；本期平台**不抽成**；广告位有数量上限与强制商业标识。
> - 钱包提升为**真正 M1**（套餐也依赖它），里程碑顺序调整为 **钱包→套餐→悬赏→咨询**。
> - 竞价系统为团队**自有、可改造的源码**，将融入本项目（具体融入形态留待 design）。

## 1. 背景与目标

### 1.1 背景

zhiguang 是一个 **AI 辅助的内容社区后端**：以 `knowpost`（知识帖）为核心内容，已具备发布流水线、关注关系（relation）、推荐 / 关注 feed（recommendation）、评论（comment）、点赞收藏计数（counter）等能力。**目前没有任何商业化 / 支付 / 广告模块**，纯内容社区。

团队拥有**一套自有的竞价系统源码**，核心能力为：给定一批候选 + 各自出价/标的，按拍卖机制选出赢家、排序并（可选）结算。该源码**可由本团队改造**，本期目标是将其融入 zhiguang。

本 PRD 定义：**如何将该竞价能力接入 zhiguang，在不破坏内容生态的前提下产生商业与激励价值。**

### 1.2 核心思路

竞价系统的本质是 **"稀缺资源的多方竞争性分配器"**。接入点不是"找一个叫拍卖的场景塞进去"，而是：

> 把 zhiguang 里"从一批候选中竞争性分配稀缺资源"的决策点找出来，**为每类资源选合适的机制——位竞价（GSP 正向）/ 付费加权 / 招投标 / 托管结算——并让竞价系统在其中承担相应角色**。

**接入现成竞价系统是本期硬性产品目标**（非可选）。各场景下竞价系统的角色不同：

- 套餐位竞价、咨询档期：竞价系统**正向模式**（选位 + 定价）。
- 悬赏：竞价系统**逆向模式**（算投标质量分，**人工仍定标**）。
- 付费加权：竞价系统**提供出价值**，喂进排序加权。

逆向模式的"winner"在悬赏中是**给提问者的参考分**，不是自动定标。

### 1.3 目标

1. 建立内容社区的**轻量变现能力**（流量位 / 咨询档期竞价）。
2. 建立**知识付费与激励闭环**（悬赏问答、付费咨询）。
3. 最大程度复用现有模块（profile / knowpost / comment / counter / relation / llm / search / storage），并将自有竞价源码融入本项目，最小化新增外部依赖。

### 1.4 非目标（本期不做）

- 接入第三方 RTB（DSP / SSP / 广告交易台）——本期只做**第一方**竞价。
- 完整的广告创意管理 / 投放后台 / DMP。
- 真实支付网关对接与完整金融合规体系——本期用**虚拟货币**跑通内循环；真金白银为后续阶段（见 §8）。
- 平台抽成（本期 0%，见 §6）。

## 3. 功能需求

接入三类稀缺资源，覆盖正向竞价与招投标两种机制。

| 功能 | 被竞争性分配的稀缺资源 | 机制 | 竞争方 | 谁定赢家 | 竞价系统角色 |
|---|---|---|---|---|---|
| 3.1 套餐流量位 | feed/search 置顶（位竞价）；feed 权重/粉丝触达（付费加权） | 正向 | 创作者（买方） | max(bid)（仅位竞价） | 正向选位+定价 / 提供出价值 |
| 3.2 付费咨询 | 专家档期 | 正向 | 用户（买方） | max(bid) | 正向选位+定价 |
| 3.3 悬赏问答 | 赏金 / 回答权 | 招投标（逆向方向） | 回答者（卖方） | **提问者人工评标** | 逆向算投标质量分（参考） |

> **工程前提**：竞价系统需支持**正向（最高价赢）**与**逆向（最优标评分）**两种模式；悬赏中逆向模式的输出是参考分，最终中标由提问者人工决定。

### 3.1 套餐流量位

将曝光资源归为**两类机制不同**的资源：

**A. 位竞价（slot auction，正向 GSP）**

- **feed 置顶位**：承接现有 `KnowPostTopPatch`，从手动指定改为竞价分配。
- **search 置顶位**：搜索结果商业位。
- 机制：**GSP 二价**——M 个位、出价高者占位、付第 M+1 价；**排期级 / 时间窗**拍卖（每窗口一次，结果缓存，对 feed 渲染零额外延迟）；**第二价一次性结算**。

**B. 付费加权（paid boost，非拍卖）**

- **推荐位权重**：`final_score = relevance_score + λ·bid`，把出价叠加到 recommendation 现有相关性分（注意防过度商业化，见 §5/§7）。
- **粉丝触达优先级**：follow-feed fanout 在收件箱容量受限时，按出价决定哪些内容优先触达。
- 机制：**不是拍卖**——无赢家、无第二价，出价线性/分段影响排序或投递权重。本期作为套餐**第二档/靠后**实现（依赖排序加权能力）。

创作者以虚拟货币出价。

### 3.2 付费咨询

- 专家档期作为稀缺资源，用户竞价抢热门时段。
- **选人**：位竞价（复用 §3.1 的 GSP / 时间窗）。
- **结算**：用户预付进托管 → 会话完成放款给专家（**P2P**，区别于套餐的"平台收钱"）。
- 复用 `profile`（专家标记）+ `relation`（关注）。
- **前置**：`profile` 当前无专家/认证标记，需新增；档期（可预约时段）实体需新建。

### 3.3 悬赏问答（招投标）

知识付费的核心，与 `knowpost`（提问）+ `comment`（回答/投标）+ `counter`（历史战绩/认可度）语义高度咬合。

**机制：招投标（tender），不是拍卖。** 提问者（买方）人工评标选人；竞价系统逆向模式只算投标质量分作参考，不自动定标。理由：知识付费标的"能否解决我这具体问题"不可机械度量。

**产品流程（状态机，高层）：**

```
[发布悬赏] 提问者预付赏金进托管(锁定前可撤回) + LLM 软准入(LLM 能答好则劝退, 不硬拦)
     ▼
[投标]   回答者投标(结构化: 战绩+方法路径+里程碑+报价, 不含解题步骤) + 锁投标质押
     │  竞价系统逆向模式 + LLM 粗筛 → 投标质量分(参考)
     ▼
[评标]   提问者基于投标质量分 + 综合判断 人工选中标者
     ▼
[锁定]   提问者锁定赏金(不可撤回)        ← 白嫖窗口在此关闭；退还未中标者质押
     ▼
[交付]   中标者交付完整答案(锁后单独提交, 独立于投标)
     ▼
[结算]   提问者确认→放款 / 超时自动放款 / 中标者跑单→退款+没收质押；提问者评分→中标者信誉
```

**注意**：本期**无"不满意→仲裁"分支**——详见 §4。

## 4. 关键设计：悬赏的信任与防白嫖

悬赏的成败取决于能否同时满足两个看似矛盾的需求：

- **甲方（提问者）**：在不看到方案的前提下，判断乙方（回答者）真能解决我的问题；
- **乙方（回答者）**：我的方案 / 劳动成果不会被甲方窃取。

设计原则：**不追求在投标阶段 100% 确定对方能力（这不现实），而是提供足够强的能力信号 + 出了问题有退路。**

借鉴真实招投标制度，并将"法律兜底"系统性替换为「经济约束 + 平台规则 + 技术存证」。

### 4.1 双向保护机制对照

| 风险 | 保护方 | 真实招投标机制 | zhiguang 落地 |
|---|---|---|---|
| 乙方没能力 / 答不好 | 提问者 | 资质预审 + 投标保证金 | **前置筛选**：历史战绩 + 投标质量分 + 投标质押（无事后退款） |
| 乙方中标后跑单 | 提问者 | 投标保证金没收 | 质押没收 + 信誉扣分（跑单=到期不交付） |
| 甲方窃取方案 | 回答者 | NDA + IP 登记 + 比稿费 | **锁定前置**（看不到完整答案）+ 平台条款 + 时间戳存证 |
| 甲方看了不付 | 回答者 | 预付款 + 履约保函 | **托管 + 锁定不可撤回 + 里程碑** |
| 甲方扣款要挟 | 回答者 | — | **超时自动放款**（提问者逾期不操作即放款给中标者） |

> **关键取舍**：本期**不设事后"不满意→仲裁"退款**。提问者防"答不好"靠**前置筛选**（评标时看战绩+质量分+人），交付后只剩**评价/信誉**作为软威慑。这使结算无争议、零仲裁运营成本。

### 4.2 三道核心防线（防"提纲被 LLM 补全后白嫖"）

**防线一：定位——悬赏只服务"LLM 答不了"的问题（信息层让白嫖不可行）**

> 若一个问题的提纲就能让 LLM 跑出不错的结果，那它本身不稀缺，不该存在为悬赏。

发布时由 LLM 自评能力边界：LLM 若能答好，则**劝退**悬赏（软提示，不硬拦）。甜区锁定在需**私有数据 / 领域经验 / 交互诊断 / 定制交付**的问题。

**防线二：隔离——"能力证明"与"答案内容"分开（砍掉危险中间层）**

- 投标只交**结构化内容**：历史战绩 + 方法路径（方法论层面，≤N 字）+ 预估里程碑 + 报价；**不含**解题步骤/源数据/可运行代码/完整推导。
- 详细解题内容**只在赏金锁定后**单独提交（独立于投标实体；锁定前平台不持有，故提问者无法提前看到）。
- 安全性靠**防线一×防线二复合保证**：防线一保证问题本身 LLM 答不好，故即便粗方向泄露，LLM 也补不出答案（能补出的话防线一就该劝退了）。

**防线三：制度——锁定前置 + 质押 + 平台补贴（改变激励）**

- 看完整答案前必须**锁定赏金（不可撤回）**，关闭白嫖窗口。
- **投标质押**：回答者投标时锁少量虚拟货币，中标后跑单则没收，未中标/正常交付则退还。
- **冷启动 / 认真投标激励**：走**平台补贴**（平台出钱给早期优质投标），不再要提问者额外预付。
- ❌ **不再设「比稿补偿池」**：v0.1 的补偿池用来防"看了不采纳"套利，但锁定前置已使提问者"不锁定就看不到完整答案"，该套利窗口本就不存在；补偿池唯一剩余价值（激励投标）由平台补贴替代，且避免了补偿池的 Goodhart 风险（刷"刚好过线"投标薅补偿）。

### 4.3 LLM 在流程中的定位（关键澄清）

LLM **不是**最终裁决者，而是**多重信号中"必要不充分"的一环**，全程**软信号 + fail-open + 不硬拦截**：

- ✅ **能做、应做**（流程前端，自动）：发布准入（劝退悬赏）、投标粗筛（合法性审查 + 领域匹配分）→ 投标质量分。
- ❌ **不做**（不可逆决策）：不单独裁决中标 / 退款。
- LLM 不可用时**放行（fail-open）**，不把流程耦合到 LLM 可用性。

理由：合法性审查管"形式有效"不管"实质能否解决"；LLM 审查可靠性 ∝ 其对该领域的能力，而悬赏恰好发生在它能力不足的领域；LLM 无 skin in the game，不能承担不可逆关键决策。最终信任落回：**资质预审（看历史）+ 经济机制（质押/托管/锁定/补贴）+ 技术存证（时间戳哈希）**。

### 4.4 存证

投标方案与最终答案提交时，平台用 `storage` 存**带时间戳的内容哈希**，作为"我先有此内容"的事后举证依据（用于判罚甲方抄袭）。**本期仅本地哈希，不上链**；上链留给真金白银阶段。

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| 性能 | 套餐 / 咨询为**排期级**竞价（每时间窗一次，结果缓存），非 per-request 实时拍卖；悬赏为状态机型，无强实时要求。 |
| 安全 / 防欺诈 | **按比例**：交易即信誉（评价只能来自真实完成交易）+ 平台补贴封顶 + 拍卖保留价 + 交易日志事后对敲检测；v1 不上设备指纹 / 重型反作弊（封闭内循环下损失上限 = 平台多发虚拟货币）。 |
| 公平 | 位竞价机制可解释（GSP 明牌）；防出价操纵 / 串标 / 抬价。 |
| 体验 | 商业位有**数量上限**（feed 每屏 ≤1 置顶、search 每页 ≤1–2）、**强制商业标识**、**单推广者频控**，避免过度商业化伤留存。 |
| 合规 | 真金白银阶段才需考虑支付牌照、资金存管、税务；本期虚拟货币无此要求。 |

## 6. 依赖与约束

- **复用**：`profile`、`knowpost`、`comment`、`counter`、`relation`、`llm`、`search`、`storage`、`cache`、`id`。
- **竞价系统**：团队**自有、可改造**的源码，本期融入本项目；需支持正向（max bid）与逆向（最优标评分）两种模式。
- **最大新增（瓶颈）**：**钱包 / 账户 + 托管状态机**。这是所有商业化功能（套餐/悬赏/咨询）的共同前置，故为真正 M1。
- **新增前置**：`profile` 专家/认证标记、专家档期实体（咨询所需）。
- **货币**：虚拟货币（封闭内循环）；**来源** = 注册发放 + 悬赏/咨询收入 + 平台补贴，不出售、不充值、不提现。
- **抽成**：本期平台**不抽成**（0%）；套餐出价即平台收入，咨询/悬赏为纯 P2P。

## 7. 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 钱包 / 托管体系缺失 | 所有商业化功能无法落地 | 钱包作为真正 M1 前置；封闭内循环使其退化为纯账本 + 托管状态机 |
| 竞价系统融入复杂度 | 接入成本 / 工期 | 自有可改源码，正向+逆向模式可自行加/调；具体融入形态 design 阶段定 |
| 过早广告化伤留存 | 用户流失 | 商业位数量上限 + 强制标识 + 频控；优先内循环而非外部广告主 |
| LLM 审查被话术操纵（Goodhart） | 投标质量分失真 | 仅作粗筛参考信号，fail-open，不单独裁决；叠加历史资质 + 经济约束 |
| 悬赏冷启动无回答者 | 功能空转 | 平台补贴激励；早期种子 |
| 咨询专家供给不足 | 功能空转 | 平台认证一批种子专家 |
| 虚拟货币通胀 / 对敲 | 经济失衡 / 信誉污染 | 补贴封顶 + 交易日志事后检测 + 交易即信誉；损失上限可控 |

## 8. 里程碑（按依赖复杂度排序）

| 里程碑 | 内容 | 依赖 | 备注 |
|---|---|---|---|
| **M1** | 钱包 / 账户 + 托管状态机（最小版） | 新建 | **所有商业化功能的共同前置**；封闭内循环 → 纯账本 + 托管，无合规 |
| **M2** | 套餐流量位（位竞价，虚拟货币） | M1 + 竞价系统正向模式 | 最简消费者（出价冻结 + 扣减），验证钱包 + 正向竞价接通 |
| **M3** | 悬赏问答（含 §4 全套机制） | M1 + 竞价系统逆向模式 + profile/knowpost/comment/counter | 语义最贴合知识社区，价值最高 |
| **M4** | 付费咨询 | M1 + M2 正向 + profile 专家标记/档期 | 复用 M2 正向 + M1 托管 |
| **M5** | 真金白银支付 / 合规 / 平台抽成 / 上链存证 | M1 扩展 | 引入支付网关、合规、存管、佣金 |

> 钱包从 v0.1 的 M2 提升为 M1：套餐位竞价也需要出价冻结/扣减，故钱包是全部商业化功能的前置。
