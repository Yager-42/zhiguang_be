# Community Closure Roadmap 13

**Goal:** 记录 `zhiguang` 后续准备推进的 `1/3` 两项能力，并明确 `4` 当前不做，作为后续立项、拆任务和实现时的统一入口。

**Scope:** 本文只记录方向、边界、优先级和落地约束，不直接替代后续单项实现计划。

**Status:** Draft

---

## Why These Three

当前 `zhiguang` 的底座已经不弱：

- 内容发布、关注、评论、计数、搜索、推荐、钱包、推广、对账都已经有骨架

现在缺的不是继续堆底层，而是补齐社区产品的用户闭环。当前优先做这两项：

1. 通知中心
2. 举报/审核闭环

不做私信的原因不是它不重要，而是 `1/3` 更适合先落地：

- `1` 直接提升回访
- `3` 直接补内容治理闭环

---

## Item 1: 通知中心

### Goal

把用户相关的核心互动统一收口，让“别人对我做了什么”变得可见。

### 用户价值

- 用户被点赞、评论、关注后能及时看到
- 用户对自己的内容状态有反馈
- 首页之外多一个可回访入口

### 初期范围

- 点赞通知
- 评论通知
- 关注通知
- 内容审核结果通知
- 未读数
- 已读/全部已读
- 通知列表分页

### 非目标

- 不做站外推送
- 不做复杂通知分组
- 不做通知推荐

### 落地约束

- 优先复用现有事件流和 Kafka/Outbox，不新增第二套消息体系
- 通知必须是独立模块，不把通知拼在各业务 controller 里临时返回
- 未读数和列表要定义清楚唯一数据源，避免多处重复维护

### 预期落点

- `src/main/java/com/tongji/notification/`
- 首页角标、个人中心入口、通知列表 API

## Item 3: 举报/审核闭环

### Goal

把“发现问题内容 -> 提交举报 -> 处理结果落地”这一条链路补齐，避免社区内容质量失控。

### 用户价值

- 用户有地方处理脏内容
- 平台能记录举报原因和处理结果
- 审核结果能反向通知用户

### 初期范围

- 举报帖子
- 举报评论
- 举报用户
- 举报原因枚举
- 举报记录落库
- 基础审核状态流转
- 审核结果通知被处理用户

### 非目标

- 不做复杂工单系统
- 不做多级审核流
- 不做外部风控平台集成

### 落地约束

- 举报对象类型必须在数据模型里显式定义，不能靠模糊字段兼容
- 审核状态机要简单：`pending -> approved/rejected/ignored`
- 后续如果接 AI 审核，也只能作为审核辅助，不改变主数据结构

### 预期落点

- `src/main/java/com/tongji/moderation/` 或 `src/main/java/com/tongji/report/`
- 举报表、审核记录表、审核结果通知

## Deferred Item 4: 用户画像 / 兴趣画像增强

### Goal

记录为什么这项当前不进入近期路线，避免后续重复误判。

### 关键结论

这项能力 **当前不做**。

### 当前事实

当前推荐链路已经存在：

- 首页混排在 `HomeFeedMixingService`
- 推荐召回由 `GorseRecommendationAdapter` 提供
- 用户资料更新会通过 `UserProfileRecommendationConsumer` 同步到 Gorse

当前问题也很明确：

- 送给 Gorse 的 `user labels` 里，真正有推荐价值的兴趣信号太薄
- 现有 `profile` 更像资料同步，不像兴趣表达

### 为什么当前不做

- `Gorse` 自己已经维护基础用户画像和推荐状态
- 本地再造一套复杂画像，如果不能被翻译成 `Gorse` 真正使用的输入，就没有现实价值
- 当前如果贸然做，会增加一套额外状态、一套同步链路和一套维护成本

### 当前决定

- 不新建复杂用户画像系统
- 不把“兴趣画像接入 Gorse”列入近期执行范围
- 继续保持 `Gorse` 是唯一推荐主脑

### 未来如果要优化推荐，正确方向

只考虑“优化 Gorse 输入信号”，不考虑另造推荐引擎：

- 更好的 `item labels`
- 更干净的 `user labels`
- 更明确的 `feedback type`
- 如果这些都不够，再评估本地 rerank，而不是先做画像系统

## Priority

建议执行顺序：

1. 通知中心
2. 举报/审核闭环

原因：

- `1` 最快形成用户回访闭环
- `3` 先补治理基础，避免内容质量先烂掉

## Implementation Rule

后续正式开始做任一项时，必须单独补一份实现计划，至少写清：

- 目标和非目标
- 数据模型
- 事件来源和唯一数据源
- API 边界
- 用户可见行为
- 验证方式

不要把这份路线文档直接当实现文档使用。
