# 知光后端开发与编码规范

| 项目 | 内容 |
|---|---|
| 版本 | 1.0.0 |
| 状态 | 生效 |
| 适用范围 | 后端代码的设计、开发、测试、评审与重构 |
| 参考基线 | FIT Framework 工程实践、阿里巴巴 Java 开发规约、项目架构契约 |

## 1. 目的与效力

本规范不绑定编程语言、框架、数据库或中间件。项目可以根据业务需要选择技术栈，但所有新增和修改代码都必须先保证正确性、安全性、数据一致性与可恢复性，再考虑性能和可维护性，最后统一代码风格。语言或框架已有官方约定时，在不违反本规范原则的前提下遵循其惯用写法。

规则分为三级：

- **强制**：违反即视为缺陷，不得合并。
- **推荐**：默认遵守；偏离时必须在设计说明或 PR 中写明理由、收益和风险。
- **参考**：根据复杂度选择，用于提高长期工程质量。

当规则冲突时，优先级为：已批准的需求或设计决策 > `ARCHITECTURE_CONTRACT.md` > 本规范 > 阿里巴巴 Java 开发规约。不能通过“现有代码就是这样写的”绕过规范；历史代码只能作为兼容性依据。

## 2. 开发总流程

任何涉及业务逻辑、存储、消息或外部系统的需求，必须按以下顺序实施：

1. 明确业务目标、输入、输出、不变量和失败语义。
2. 列出正常流程、异常流程、边界条件和并发冲突。
3. 设计接口、状态机、一致性、幂等、失败恢复和可观测性。
4. 评估数据规模、计算复杂度、资源消耗和外部依赖容量。
5. 先确定测试场景，再实现最小完整逻辑。
6. 完成自测、静态检查、代码评审和文档同步。

## 3. 架构与分层

以下名称表示职责，不要求使用特定框架，也不要求目录必须同名；采用其他架构风格时必须保持等价的职责隔离和单向依赖：

```text
Controller / Consumer
        -> Service
        -> Manager / Domain Component
        -> Mapper / Repository / External Adapter
```

| 层 | 职责 | 禁止事项 |
|---|---|---|
| Controller | 鉴权上下文、协议转换、参数格式校验、调用 Service、返回统一响应 | 业务计算、事务、直接调用 Mapper、拼装查询语句 |
| Consumer | 反序列化、基础校验、幂等入口、调用 Service、确认或重试消息 | 承载复杂业务、无界重试、吞异常 |
| Service | 用例编排、业务规则、状态机、事务边界、权限校验 | 依赖 Controller DTO、拼接 SQL、直接使用具体外部客户端散落各处 |
| Manager / Domain Component | 多 Mapper 组合、可复用领域能力、缓存和外部系统封装 | 暴露 HTTP 概念、绕过领域不变量 |
| Mapper / Repository | 明确的数据读写、结果映射、原子条件更新 | 业务决策、跨模块访问、返回无类型 `Map` |
| External Adapter | 隔离第三方协议，统一超时、重试、错误转换和指标 | 向业务层泄漏 SDK 类型和底层异常 |

- **强制**：依赖必须显式传入并尽可能保持不可变，禁止依赖由隐式全局状态或不可追踪的运行时修改产生。支持构造器注入的语言和框架优先使用构造器注入。
- **强制**：接口与实现按稳定边界创建，不为每个类机械增加无意义接口。
- **强制**：跨模块调用仅依赖公开契约或事件，不依赖对方实现类、数据访问对象、持久化对象或内部组件。
- **推荐**：方法只做一个可命名的动作。业务主流程使用早返回，嵌套通常不超过 3 层。

## 4. 编码规范

### 4.1 命名与模型

命名首先遵循所用语言的官方风格。对于采用 Java/C# 类命名习惯的语言，类型使用 `UpperCamelCase`，方法、参数、字段和局部变量使用 `lowerCamelCase`，常量使用 `UPPER_SNAKE_CASE`，包名全小写；其他语言采用其标准等价形式。

- **强制**：名称表达业务含义，禁止拼音、无意义缩写和 `data`、`info`、`obj`、`temp`、`handle` 等无法说明职责的泛化命名。
- **强制**：测试、异常和枚举遵循语言生态的惯用命名，使类型角色可以从名称直接识别。
- **强制**：持久化模型、接口输入输出模型、传输模型和领域模型必须职责分离。具体后缀遵循项目约定，禁止一个对象贯穿协议、业务和持久化各层。
- **强制**：布尔字段按照所用语言和序列化框架的惯例命名，确保代码属性名与传输字段名映射明确且稳定。
- **强制**：禁止魔法值。常量按领域归属放置，禁止创建无限膨胀的 `CommonConstants`。

### 4.2 格式与结构

沿用 FIT Framework 的统一格式化基线：

- **强制**：文本文件使用 UTF-8 和 LF，单行不超过 120 个字符；缩进宽度、Tab 使用和换行规则由项目格式化工具统一，禁止个人覆盖。
- **强制**：使用大括号表示代码块的语言中，`if`、`for`、`while` 等即使只有一行也必须使用大括号。
- **强制**：支持导入语句的语言禁止通配符导入；静态导入、第三方包、标准库分组，组内按名称排序。
- **强制**：支持顶级类型的语言中，一个文件只定义一个主要公开类型；成员顺序遵循项目格式化配置或语言惯例。
- **推荐**：同一语义块内不插空行，不同阶段之间只保留一个空行。
- **推荐**：链式调用按阶段换行；复杂布尔表达式提取为有业务含义的方法或变量。

### 4.3 注释规范

注释的目标是补充代码无法清晰表达的设计意图、业务约束和风险。好注释回答“为什么这样做”“适用边界是什么”“违反后会怎样”，不逐行翻译代码。

本节示例使用当前参考仓库的 Java 文档注释语法；使用其他语言时必须转换为该语言的标准文档注释格式，表达内容不变。

#### 4.3.1 必须写注释的场景

- **强制**：公开类型、接口和公开或受保护方法必须写文档注释。所用语言没有 Javadoc 时，使用该语言的标准文档注释格式。
- **强制**：复杂业务规则、状态流转、计算公式、兼容逻辑、临时绕行、并发控制和不直观的性能优化必须在实现附近说明原因。
- **强制**：单位、精度、时区、有效期、取值范围、特殊常量和位标记无法由名称完整表达时必须注释。
- **强制**：方法可能返回空值、空集合、特殊值或抛出业务异常时，必须在方法契约中说明触发条件。
- **强制**：调用外部接口、修改共享状态或执行不可逆操作时，必须说明幂等性、副作用和失败处理方式。
- **推荐**：简单的私有方法、语义明确的字段和一眼可见的控制流不写注释，以清晰命名代替注释。

#### 4.3.2 类和接口注释

类或接口注释应包含：

1. 一句话说明职责，不使用“这是一个……类”之类空话。
2. 说明负责什么，以及明确不负责什么。
3. 必要时说明生命周期、线程安全性、状态约束和主要协作者。
4. 核心领域类型添加 `@since yyyy-MM-dd`；作者归属由版本控制记录，不强制新增 `@author`。

```java
/**
 * 管理钱包账户的余额冻结与解冻。
 *
 * <p>仅维护账户余额和流水的一致性，不负责支付渠道调用。实例无可变状态，可安全地被并发调用。</p>
 *
 * @since 2026-08-07
 */
public class WalletBalanceService {
}
```

#### 4.3.3 方法注释

方法注释先用一句话描述可观察行为，再根据需要补充前置条件、副作用、幂等性和并发语义。标签写法如下：

- `@param`：说明业务含义，并写清单位、格式、范围及是否允许为空；禁止只写“参数 ID”。
- `@return`：说明返回结果及空值、空集合、特殊值语义；无返回值时不写。
- `@throws`：说明异常类型及精确触发条件，不能只写“操作失败时抛出”。
- `@since`：只用于需要记录引入版本或日期的公开契约，不要求每个方法都写。

```java
/**
 * 冻结指定账户的可用余额；相同业务流水号重复调用时返回首次处理结果。
 *
 * @param accountId 账户 ID，不允许为 {@code null}
 * @param amountInCent 冻结金额，单位为分，取值范围为 [1, 100000000]
 * @param businessRef 业务流水号，在同一账户内唯一，不允许为空白字符串
 * @return 冻结成功后的账户余额快照，不返回 {@code null}
 * @throws BusinessException 当账户不存在、余额不足或账户状态不允许冻结时
 */
public WalletBalance freeze(Long accountId, long amountInCent, String businessRef) {
    // 方法实现
}
```

#### 4.3.4 字段和常量注释

- **强制**：字段注释描述业务含义，不重复字段类型和名称。
- **强制**：时间、金额、容量等数值字段必须通过名称或注释说明单位。
- **强制**：常量注释说明来源和选择该值的理由；行业标准、协议或需求编号可以附引用。
- **推荐**：`private static final int MAX_RETRY_COUNT = 3` 这类名称已完整表达语义的常量不需要“最大重试次数”式重复注释，但应在重试策略处说明为什么是 3 次。

#### 4.3.5 行内和代码块注释

- **强制**：注释放在所解释代码块之前，与代码保持相同缩进；避免在行尾堆叠长注释。
- **强制**：解释反直觉实现时，同时说明不能采用直观方案的原因。
- **强制**：修改代码时同步修改相关注释。失效注释比没有注释风险更高。
- **强制**：禁止保留被注释掉的代码、调试代码和无上下文的历史说明，历史由版本控制保存。

```java
// 先登记业务流水再更新余额，利用唯一约束保证并发重试只产生一笔流水。
ledgerRepository.insert(accountId, businessRef, amountInCent);
balanceRepository.freeze(accountId, amountInCent);
```

以下注释没有提供额外信息，禁止使用：

```java
// 遍历列表
for (Order order : orders) {
    // 设置状态
    order.setStatus(COMPLETED);
}
```

#### 4.3.6 TODO、FIXME 和临时方案

- **强制**：`TODO` 表示计划内改进，`FIXME` 表示已知缺陷或风险；二者必须包含负责人、日期、原因和可追踪任务编号。
- **强制**：临时兼容代码必须注明删除条件或截止版本，不能只写“后续优化”。
- **强制**：没有负责人或任务编号的 TODO 不得新增；阻塞正确性或安全性的问题不得以 TODO 代替修复。

```java
// TODO(zhangsan, 2026-08-07, ZG-128): 旧客户端全部升级到 v3 后删除字段兼容逻辑。
// FIXME(lisi, 2026-08-07, ZG-135): 当前算法在闰日会重复结算，发布前必须修复。
```

#### 4.3.7 语言与排版

- **强制**：内部代码注释使用中文，标识符、协议名和专有技术名保留原文。
- **强制**：使用完整句子和正常标点；中英文之间保留一个空格，代码标识符使用文档格式标记。
- **推荐**：一行不超过 120 个字符；长说明分段表达，避免在单个注释块中写设计文档。

### 4.4 空值、集合与类型

- **强制**：方法契约必须区分 `null`、空集合、空字符串和不存在。集合返回值默认返回空集合，不返回 `null`。
- **强制**：区分引用相等与值相等，按语言规则使用正确的比较方式；精确小数使用精确数值类型及其数值比较方法。
- **强制**：访问数组或列表下标、可选值、Map 值或进行可能失败的类型转换前，必须先证明值存在且类型合法。
- **强制**：重写 `equals` 必须同时重写 `hashCode`；用作 Map key 或 Set 元素的对象在生命周期内保持参与比较字段不变。
- **强制**：禁止在增强 `for` 中修改集合；批量集合必须限制大小并预估初始容量。
- **推荐**：对“必然存在”的内部不变量使用前置校验；对业务上“可能不存在”的结果使用清晰的空对象、`Optional` 或业务异常，避免层层猜测。

## 5. 鲁棒性与逻辑边界

### 5.1 入参与不变量

FIT Framework 使用统一校验工具在对象入口处快速失败。本规范采用这一原则，但不指定校验框架或异常类型。

- **强制**：协议入口校验格式和范围，应用或领域层再校验权限、状态和跨字段业务规则。
- **强制**：所有公开方法在入口验证必需参数和不变量，不允许非法值深入调用链后以 NPE 失败。
- **强制**：分页大小、批量大小、字符串长度、数值范围、时间跨度、排序字段和文件大小必须有上限。
- **强制**：服务端从认证上下文获取用户身份，不信任客户端传入的 ownerId、userId 或角色。
- **强制**：所有状态变更使用显式状态机或条件更新；非法转换返回稳定业务错误，禁止直接覆盖状态。

### 5.2 必查边界

每个分支都应检查与业务相关的以下边界：

- `null`、空字符串、空集合、零值、负值、最小值、最大值和溢出；
- 记录不存在、已删除、重复记录、状态过期、版本冲突和权限不足；
- 首条、末条、跨页、无下一页、大分页和排序字段相同；
- 首次请求、重复请求、并发请求、乱序消息、迟到消息和重复消息；
- 外部依赖超时、限流、部分成功、返回空结构和返回未知枚举；
- 事务提交失败、消息发送失败、缓存失效、进程重启和补偿重复执行。

### 5.3 异常处理

- **强制**：禁止捕获 `Exception` 后吞掉、仅打印或返回 `null`。无法在当前层恢复时保留 cause 并转换为该层稳定异常。
- **强制**：业务可预期失败使用明确的领域异常和稳定错误码；系统故障由统一异常边界转换，禁止向客户端暴露堆栈、查询语句或内部地址。
- **强制**：catch 范围只包围可能失败的语句。禁止用异常实现普通分支控制。
- **强制**：使用语言提供的作用域资源管理机制自动关闭资源；不支持时在可靠的清理块中关闭。清理失败不得覆盖主异常。
- **强制**：新增重试前必须证明操作幂等，并设置最大次数、退避、抖动和总超时。参数错误、权限错误和确定性业务错误不得重试。

## 6. 数据访问与持久化

以下规则仅在使用关系数据库或 SQL 时适用；采用文档库、键值存储、搜索引擎或其他持久化方案时，应遵循相同的明确模型、原子性、容量和可恢复性原则。

### 6.1 表与字段

- **强制**：表和字段使用小写下划线；表名使用单数；主键、唯一索引、普通索引分别使用 `pk_`、`uk_`、`idx_` 前缀。
- **强制**：业务唯一性由数据库唯一索引兜底，应用层预查不能替代唯一约束。
- **强制**：精确数值使用精确十进制类型或整数最小单位；时间字段、时区和精度在存储类型与代码类型间保持一致。
- **强制**：DDL 必须包含字段注释、默认值理由、索引、数据迁移、回滚或前向修复方案，并评估锁表影响。
- **推荐**：不使用数据库外键和级联，由应用层维护关系并通过对账发现漂移。

### 6.2 查询与写入

- **强制**：禁止 `SELECT *`，只查询需要的字段并映射为明确类型。
- **强制**：使用驱动、ORM 或查询框架提供的参数绑定能力。禁止把用户输入直接拼接到查询语句；动态表名、列名和排序字段必须经过服务端白名单映射。
- **强制**：查询条件超过两个时使用 Query 对象，禁止使用 Map 传递未定义结构。
- **强制**：更新语句只更新明确字段；状态流转和并发写采用 `WHERE id = ? AND status = ?`、版本号或等价 CAS 条件，并校验影响行数。
- **强制**：批量 `IN`、批量插入和更新必须分片并设置上限；不得让请求规模直接决定 SQL 长度。
- **强制**：分页使用稳定且唯一的排序。深分页优先游标或延迟关联，禁止无限 offset 扫描。
- **强制**：三表及以上实时 JOIN 必须在设计评审中说明必要性、基数、索引和 EXPLAIN 结果。
- **强制**：`COUNT(*)` 表示行数；聚合函数必须显式处理 `NULL`。查询总数为 0 时不再执行分页数据查询。
- **推荐**：列表查询采用批量查询和 Map 组装，禁止循环内逐条查询形成 N+1。

### 6.3 查询性能证据

新增或改变核心查询时，PR 必须附：

- 代表性参数和数据规模；
- SQL 与索引选择理由；
- `EXPLAIN` 或 `EXPLAIN ANALYZE` 结果；
- 预计扫描行数、返回行数和排序/临时表情况；
- 慢查询风险以及数据增长后的退化点。

执行计划应使用有效索引并控制扫描范围。具体访问类型目标按所用数据库的执行计划定义确定，无法避免全量扫描时必须说明原因和容量上限。

## 7. 事务、一致性与并发

- **强制**：事务边界放在应用用例或业务操作边界，事务中只包含必须原子提交的操作。
- **强制**：事务内禁止 HTTP/RPC、对象存储上传、搜索写入、消息直发和无界循环，避免长事务和不可回滚副作用。
- **强制**：使用异步消息时必须明确投递语义。至少一次投递的消费者必须实现幂等；需要保证业务写入与事件发布一致时，使用事务消息、outbox 或具备同等保证的机制。
- **强制**：幂等必须由 `业务键/请求键 + 唯一约束或原子操作 + 重复结果定义` 三部分组成，不能只依靠短期分布式锁。
- **强制**：写后检查影响行数。期望更新一行却更新 0 行表示状态冲突或记录不存在，更新多行表示约束或 SQL 错误。
- **强制**：明确并发控制策略。优先唯一约束、条件更新、版本号和数据库原子操作；仅在必要时使用悲观锁或分布式锁。
- **强制**：锁必须有明确粒度、顺序、超时和释放策略；持锁期间禁止调用不受控外部服务。
- **强制**：事件消费者必须处理重复、乱序、迟到和毒消息，失败进入有限重试、死信或对账流程。
- **推荐**：缓存更新采用失效、版本化或可靠事件，禁止没有一致性说明的数据库与缓存双写。

## 8. 性能与资源

- **强制**：优化前先定义指标和数据规模；优化后提供相同条件下的测量结果。禁止只凭感觉宣称“高性能”。
- **强制**：禁止无界集合、无界队列、无界缓存、无界线程创建和无界重试。
- **强制**：线程由有名称的受管线程池提供，并明确核心线程数、最大线程数、队列、拒绝策略和关闭方式。
- **强制**：网络、数据库、锁和异步任务必须配置超时。连接池和线程池容量要匹配下游承载能力。
- **强制**：缓存必须定义 key 结构、value schema、TTL、最大规模、击穿/穿透/雪崩策略和重建方式。
- **强制**：大对象、大结果集和文件使用流式或分页处理，资源使用 try-with-resources。
- **推荐**：先消除 N+1、重复序列化、重复远程调用、全表扫描和锁竞争，再考虑微观代码优化。
- **推荐**：性能敏感路径补充基准或压测，记录 P50/P95/P99、吞吐、错误率、CPU、内存和下游压力。

## 9. 日志、监控与安全

### 9.1 日志与指标

- **强制**：使用项目统一的日志接口；优先使用占位符、结构化字段或延迟参数，禁止为未启用的日志级别提前拼接字符串。异常日志同时记录业务上下文和完整异常对象。
- **强制**：日志包含可关联标识，如 traceId、userId、entityId、requestId、eventId 或 businessRef，但不得记录密码、Token、密钥、完整手机号和身份证等敏感数据。
- **强制**：同一异常只在能够处理或统一收口的层级记录一次，避免每层重复打印堆栈。
- **强制**：关键业务动作记录结果和原因；高频循环内禁止逐条 INFO 日志。
- **强制**：新增关键链路同步增加成功率、失败率、耗时、积压、重试、死信或对账指标，并定义告警阈值。

### 9.2 安全

- **强制**：所有接口执行认证、对象级授权和操作级授权，防止水平与垂直越权。
- **强制**：用户输入必须校验；动态排序、跳转地址、文件类型、正则、反序列化类型均使用白名单。
- **强制**：敏感数据按最小必要原则查询、传输、展示和记录；响应和日志必须脱敏。
- **强制**：短信、邮件、登录、发布、支付、钱包等高价值操作必须防重放、防刷并限频。
- **强制**：密钥和凭证只能来自受控配置或密钥服务，禁止提交到仓库或写入日志。

## 10. 接口、消息与兼容性

- **强制**：输入与输出类型分离；禁止直接暴露持久化对象、数据访问对象或第三方 SDK 类型。
- **强制**：接口状态、业务错误码和错误信息遵循统一错误契约，各入口不得自造不兼容的错误响应。
- **强制**：跨语言传输数值时评估接收方的精度范围；超过接收方安全整数范围的 ID 使用字符串或无损协议类型传输。
- **强制**：列表响应定义稳定排序、分页方式、最大页大小和空结果结构。
- **强制**：事件必须包含 eventId、eventType、schemaVersion、occurredAt、业务键和 payload；消费者兼容未知字段。
- **强制**：删除或修改公开字段、枚举、错误码、主题和事件语义前必须完成兼容性评估和迁移计划。
- **推荐**：新增字段保持向后兼容；废弃项标注替代方案和移除版本，不直接删除。

## 11. 测试规范

FIT Framework 的测试按行为分组，并覆盖资源获取、提交、回滚和清理失败。本项目沿用这种以场景和失败路径为中心的测试方式。

- **强制**：测试名称必须表达“条件下的预期行为”。语言允许时，测试类型以被测类型命名，测试方法可采用 `should_expected_when_condition`；展示名称使用中文描述行为。
- **强制**：每项业务规则至少覆盖正常路径、关键边界、非法状态和依赖失败；修复缺陷必须先增加可复现测试。
- **强制**：金额、计数、状态机、幂等、事务和补偿逻辑必须测试重复执行、并发冲突和失败恢复。
- **强制**：数据访问组件或复杂查询使用集成测试验证真实映射、唯一约束、事务和边界数据；不能只使用 Mock 证明其正确性。
- **强制**：测试必须可重复、互相隔离，不依赖执行顺序、真实时间、随机网络或共享脏数据。
- **强制**：只验证可观察行为，不为提高覆盖率绑定私有实现细节。
- **推荐**：使用测试框架的分组能力按前置状态组织场景，采用 Arrange-Act-Assert 结构；每个测试只验证一个清晰行为。
- **推荐**：关键并发路径增加集成测试或压测，不能用单线程单元测试证明并发安全。

提交前必须执行项目约定的完整单元测试命令。涉及数据库、缓存、消息系统、搜索服务、对象存储或容器编排的变更，还必须执行对应集成测试；不能执行时在 PR 中说明原因和剩余风险。

## 12. Git、评审与交付门禁

### 12.1 变更原则

- **强制**：一次变更只解决一个主题，不夹带无关重构、格式化或依赖升级。
- **强制**：提交信息采用 `<type>(<scope>): <subject>`，如 `fix(wallet): 修复重复入账`。
- **强制**：依赖版本集中管理；升级前后比较依赖树、安全公告和兼容性，生产代码不得依赖未批准的快照版、开发版或其他不稳定版本。
- **强制**：数据库、配置、接口、事件或架构边界变化必须同步文档、脚本和测试。

### 12.2 评审顺序

评审者按以下顺序检查，不得只检查格式：

1. 正确性、安全与权限。
2. 数据来源、表归属、聚合公式和一致性。
3. 异常边界、状态机、事务、幂等与可恢复性。
4. SQL、索引、并发、资源上限和性能。
5. 分层、命名、注释、重复代码和风格。
6. 测试证据、监控、文档与发布回滚。

### 12.3 Definition of Done

合并前必须全部满足：

- [ ] 正常、异常、边界、并发和重复场景已覆盖。
- [ ] 分层和跨模块依赖符合架构契约。
- [ ] 涉及数据查询时，无注入、无无界字段读取、无明显 N+1，核心查询有执行计划或等价性能证据。
- [ ] 事务范围最小，外部副作用、幂等、重试和补偿设计明确。
- [ ] 日志无敏感信息，关键路径有指标和可关联标识。
- [ ] 单元测试和相关集成测试通过。
- [ ] 代码已按统一格式化规则处理，无无关变更。
- [ ] 接口、DDL、配置、事件和架构文档已同步。
- [ ] 发布、兼容和回滚风险已说明。
