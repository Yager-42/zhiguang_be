# Design: split-to-microservices

> 本变更为纯架构指导，不修改运行时代码。所有决策作为第一批实现变更的约束条件。

## 关键决策

### 1. 数据库策略：按边界建表，物理共库

第一批继续共享 MySQL，但每张表归属明确，**禁止跨边界直接 JOIN**：

| 服务边界 | 表前缀/归属 |
|---------|------------|
| 内容服务 | `know_posts`, `publish_attempt` |
| 评论服务 | `comments`, `pending_comments` |
| 关系服务 | `following`, `follower` |
| 计数服务 | （Redis 为主，无独立 MySQL 表） |
| 搜索服务 | （ES 为主，无独立 MySQL 表） |
| 存储服务 | （MinIO + Cassandra，无 MySQL 表） |
| ID 服务 | `leaf_alloc` |
| 任务调度服务 | `reconciliation_task`, `reconciliation_checkpoint`, `reconciliation_error_log` |

跨边界数据需求通过 API 调用或事件获取，不写跨服务边界的 JOIN 查询。未来分库时只需搬表，不需重构查询逻辑。

### 2. 服务间通信：按场景混用

| 场景 | 通信方式 |
|------|---------|
| 查询（读取其他服务数据） | 同步 HTTP / Feign |
| 写入通知、派生任务触发 | 异步 Kafka 事件 |
| 跨服务强一致操作 | 同步 HTTP（谨慎使用） |

第一批代码已在遵循此模式：发布用 Kafka，搜索读用 HTTP。新模块继续保持。

### 3. 拆分触发条件：团队 + 负载双重压力

满足以下**任意两条**时启动拆分评估：

1. 某模块有 2+ 名开发者同时频繁修改，合并冲突成为瓶颈
2. 某模块出现独立扩容需求（如评论写入、搜索查询量远超其他模块）
3. 某模块部署频率需要与主服务解耦（发布窗口独立）
4. 某模块需要独立的技术栈或语言

单一条件不足以支撑拆分成本，过早拆分引入不必要的分布式复杂度。

### 4. 拆分顺序：搜索/推荐优先

推荐拆分顺序：

```
第 1 步：搜索 & 推荐服务
  └─ 理由：依赖 ES/Gorse 独立基础设施，API 以查询为主，对主服务影响小，风险最低

第 2 步：评论服务
  └─ 理由：写入量大，扩容动机强，与主服务通过事件交互已隔离

第 3 步：任务调度服务（对账）
  └─ 理由：完全后台运行，无用户侧 API 依赖，拆分对用户无感知

第 4 步：关系 & 计数服务
  └─ 理由：Redis 密集，独立后可按需扩 Redis 集群

第 5 步：内容服务 & 用户/认证服务
  └─ 理由：最核心，依赖最多，留到最后降低影响面
```

**不推荐**优先拆认证/用户服务——所有服务都依赖它，先拆会让其他服务立刻依赖一个外部服务，风险最高。

### 5. Gateway 与服务注册：Spring Cloud Gateway + Nacos

技术选型：Spring Cloud Gateway（路由、限流、认证前置） + Nacos（服务注册与发现、配置中心）。

- 与现有 Spring Boot 技术栈天然集成
- Nacos 同时承担配置中心，可替代部分 `application.yml` 环境变量

> **当前不实现**，记录为未来拆分时的技术方向。

## 第一批实现的约束

新增模块必须遵守：

1. **不跨服务边界 JOIN**：跨边界数据用接口或事件，不用 SQL JOIN
2. **外部依赖走 Adapter**：Gorse、ES、Cassandra 等外部系统通过接口隔离（`RecommendationEngine`、`TextStorageService` 等），不直接散落在业务代码中
3. **写入用事件**：跨边界的写入通知优先走 Kafka，不直接调用其他模块的 Service 实现类
4. **ID 不共享生成器**：各边界通过 `IdService` 按 namespace 生成 ID，不直接实例化生成器

这些约束确保第一批单体代码未来可以按边界拆分，而无需重构核心逻辑。
