## Context

zhiguang 现有主域是内容社区，只有 `user` 主身份，没有商业化账务能力。PRD 已确定虚拟货币为本期唯一出价单位，平台不接支付网关、不做提现，但需要支持平台发币、平台补贴、推广扣费、悬赏托管和质押没收。`bytedance` 现有后端包含钱包、冻结和结算代码，但其原模型绑定独立 `account` 身份与拍卖场景，需要按 zhiguang 语义改造。

## Goals / Non-Goals

**Goals:**
- 建立绑定 `user` 的统一钱包语义，覆盖可用、冻结、托管三态。
- 建立平台账本主体，保证平台发币、补贴、套餐收入和罚没都可平账。
- 建立通用托管状态机，供悬赏等业务复用。
- 保持交易流水只追加，作为后续对账与审计事实源。

**Non-Goals:**
- 不引入真实支付、充值、提现、税务或资金存管。
- 不引入第二套商业身份、认证、用户主表或运营账号体系。
- 不在本 change 内落具体推广、悬赏业务流程。

## Decisions

### 1. 钱包归属绑定现有 `user`

钱包主体直接复用 zhiguang `user.id`。不迁入 `bytedance` 的 `account/account_credential/auth_session` 认证域，也不在 zhiguang 中增加第二套商业主身份。

备选：
- 保留 `bytedance account` 作为商业主体：会与现有认证体系冲突，且违背“zhiguang 业务优先”。
- 每个业务单独维护余额：会让推广、悬赏、补贴之间无法共用余额与对账语言。

### 2. 平台账本主体是一等记账主体，但不是用户身份

平台账本主体只存在于账务系统内，用于：
- 发注册赠币
- 发平台补贴
- 接收套餐成交收入
- 接收质押罚没
- 作为托管过桥对手方

它不是普通 `user`，也不进入内容社区身份模型。

### 3. 钱包采用“余额快照 + 只追加流水”组合

保留用户钱包余额快照，满足高频读；同时记录只追加流水，作为事实源。每次发币、冻结、释放、托管划转、退款、罚没都写流水，余额快照只是加速读取视图。

备选：
- 只有流水，读时重放求余额：语义最纯，但对当前单体读路径过重。
- 只有余额快照，不记流水：后续无法做对账、补偿与审计。

### 4. 通用托管状态机独立于具体业务

托管单据抽成通用能力，记录付款方、收款方、平台账本主体、业务引用、金额、状态和过期时间。业务只驱动状态迁移：
- `created`
- `locked`
- `released`
- `refunded`
- `forfeited`
- `cancelled`

悬赏的评标、锁定、跑单是业务语义；资金迁移由统一托管状态机承接。

### 5. 本期货币来源和去向严格受限

本期只支持：
- 注册赠币
- 平台补贴
- 推广支出
- 悬赏/后续业务收入转移
- 退款/罚没

明确不支持充值、提现、外部支付回调。API 级别和规格级别都不暴露这些动作。

## Risks / Trade-offs

- [平台账本主体不是用户] → 需要在代码和文档里反复约束，避免后续被误用为第二套身份系统。
- [余额快照与流水双写] → 需要事务内更新和幂等键，后续由对账任务补洞。
- [托管能力先于具体业务落地] → 需要控制抽象层级，避免做成空泛“支付平台”。
- [改造 `bytedance` 钱包代码] → 必须剥离其拍卖和独立认证假设，否则会把旧业务模型带入 zhiguang。
