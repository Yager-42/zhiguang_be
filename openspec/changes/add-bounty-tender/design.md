## Context

zhiguang 现有最接近悬赏问答的能力是 `knowpost`、`comment`、`llm` 和 `counter`，但这些模块都不直接表达“结构化密封投标”“锁定后交付”“托管放款”“跑单罚没”等业务语义。PRD 又已经明确：悬赏不是逆向拍卖自动定标，而是人工评标的招投标。`bytedance` 的逆向竞价能力只能作为评分引擎被改造接入，不能主导业务决策。

## Goals / Non-Goals

**Goals:**
- 建立独立悬赏单、投标书、交付物和评分模型。
- 让逆向竞价能力只负责投标质量分参考，不自动定标。
- 用统一托管、质押、补贴和罚没模型支撑无争议结算。
- 保持 LLM 作为软信号且 fail-open。

**Non-Goals:**
- 不把投标复用成公开 `comment`。
- 不支持交付后仲裁退款。
- 不让 LLM 或逆向评分引擎单独决定中标或退款。

## Decisions

### 1. `bounty`、`bounty bid`、`bounty submission` 分离建模

悬赏单是业务主单；投标书是结构化密封报价；交付物是锁定后提交的完整答案。三者生命周期、可见性和存储结构都不同，不能复用同一个 `comment` 实体。

### 2. 悬赏绑定提问型 `knowpost`，但不等同于帖子

问题帖子仍由 `knowpost` 提供内容承载、公开讨论和发现入口；悬赏单记录赏金、评标、锁定、交付与结算状态。这样既复用内容社区入口，也保持商业业务单据独立。

### 3. 逆向竞价系统只产出质量分，不产出中标决策

`bytedance` 逆向模式接入后，只输出投标质量分。中标动作必须由提问者人工执行。这样既满足“接入现成竞价系统”硬性目标，也不让机械评分越过知识付费场景的判断边界。

### 4. LLM 只做软准入和软粗筛，且 fail-open

发布悬赏时，LLM 可给出“这个问题 LLM 可能已能解”的劝退信号；投标阶段，LLM 可做合法性与领域匹配粗筛。LLM 不可用时流程继续，不阻塞悬赏发布、投标或评标。

### 5. 结算采用锁定前置 + 质押 + 无争议终态

核心账务路径：
- 提问者先托管赏金
- 回答者投标时锁质押
- 提问者人工定标后锁定悬赏
- 中标者提交交付物
- 提问者确认或超时自动放款
- 跑单则退款并罚没质押

不支持“交付后不满意再仲裁退款”。

### 6. 投标与交付都需要内容哈希存证

投标书和交付物提交时都写入时间戳内容哈希，作为“我先有此内容”的事后证据。存证依赖本地哈希和对象存储，不引入上链。

## Risks / Trade-offs

- [不复用 comment] → 会新增一组完整表与 API，但这是避免语义污染的必要成本。
- [人工定标] → 自动化程度较低；但符合 PRD 对知识付费信任模型的要求。
- [无仲裁退款] → 降低运营成本，但把更多防风险压力前移到评标、质押和信誉。
- [LLM fail-open] → 可能放过低价值悬赏或低质量投标；但避免把关键流程绑死在 LLM 可用性上。
