# zhiguang_be 压测方案

> 目标：定位当前实现（代码现状）的性能瓶颈；建立**常态服务指标**与**高压服务指标**基线（QPS / TPS / 延迟 / 错误率 / 资源水位），为容量规划与后续优化提供量化依据。
> 工具：k6（HTTP 压测）+ 服务端采样脚本（Redis / MySQL / Kafka / Cassandra / Docker stats）。
> 本目录结构：

```
loadtest/
├── 压测方案.md          # 本文档（为什么压、压什么、指标口径、瓶颈判定）
├── README.md            # 操作手册（怎么装、怎么跑、怎么读结果、参数速查、FAQ）
├── DEPLOY.md            # 部署指南（中间件 + 应用从零跑起来，含排障）
├── run.sh               # 编排：seed / baseline / mixed / soak / all（每阶段双采样）
├── collect_metrics.sh   # SUT 侧指标采样器（Redis/MySQL/Kafka/ES/应用健康）
├── loadgen_metrics.sh   # 压测机侧指标采样器（CPU/内存/网络/TCP/FD，判测量是否失真）
├── scripts/             # k6 场景脚本
│   ├── common.js        # 公共配置/登录/请求包装/工具
│   ├── auth.js          # 登录、/me、刷新令牌
│   ├── feed.js          # 公共 Feed / 关注 Feed / 我的 / 详情（三级缓存读路径）
│   ├── counter.js       # 点赞/收藏写 + 计数读（位图 Lua + Kafka + SDS）
│   ├── comment.js       # 评论提交（异步写）/ 评论列表
│   ├── relation.js      # 关注/取关/状态/列表（令牌桶限流写）
│   ├── search.js        # 搜索 / 联想（ES）
│   ├── wallet.js        # 钱包余额/流水（FOR UPDATE 行锁）
│   ├── promotion.js     # 竞价收单（RocketMQ→Redis Lua→Kafka→MySQL）
│   ├── mixed.js         # 混合用户旅程（常态基线主场景）
│   └── soak.js          # 长稳（2h，观测定时任务与键空间增长）
├── seed/                # 种子数据

│   ├── seed_promotion.sql    # 推广活动 + 竞价窗口

└── results/             # 压测输出（k6 JSON + 指标 TSV）
```

配套（仓库根目录）：`Dockerfile` + `docker-compose.yml`（含 `app` 服务）—— `docker compose up -d --build` 一键部署（见 `loadtest/DEPLOY.md`）。

## 2. 被测系统与环境

### 2.1 拓扑（docker-compose 本地全栈）

| 组件 | 角色 | 压测相关配置 |
|---|---|---|
| 应用 `:8080` | Spring Boot 单实例 | HikariCP `maximum-pool-size: 10`（重要瓶颈候选） |
| MySQL `:3306` | 主存储 + outbox | 种子数据落库 |
| Redis `:6379` | 计数 SDS/位图、Feed 缓存、单飞协调、令牌桶、通知桶 | 单实例 |
| Kafka `:9092` | counter-events / comment-write / canal-outbox / decision | 单 broker |
| RocketMQ `:9876/10911` | B' 竞价命令 | 竞价场景需要 |
| Cassandra `:9042` | feed_inbox / author_feed / 正文文本 | 关注 Feed 场景需要 |
| ES `:9200` | 搜索索引 | 搜索场景需要（应用启动时自动回填） |
| MinIO `:9000` | 对象存储 | 预签名场景（P2，可不压） |
| Canal | MySQL binlog → Kafka 桥接 | **本地默认关闭（`canal.enabled=false`）** |

### 2.2 环境开关与限制

| 开关 | 默认 | 说明 |
|---|---|---|
| `PROMOTION_BPRIME_ENABLED` | false | 竞价全链路（RocketMQ）压测必须置 true |
| `GORSE_ENABLED` | false | 推荐源默认关；开则读路径带 300ms 外部依赖（降级压测用） |
| `canal.enabled` | false | **本地关闭 → outbox→Kafka 桥接不通**：关注/发布的 fanout 与搜索索引消费链在本地只能压到「写入 outbox」为止。全链路 fanout 需在 Canal 开启的测试环境压（方法见 6.3） |
| `MODERATION_LLM_ENABLED` | false | LLM 审核默认关；开则发布链路带外部 LLM 调用（P2） |

### 2.3 压测机资源保障（四层，详见第 10 章）
- **架构隔离**：正式基线/高压阶段压测机与 SUT **物理分离**（不同机器，千兆网）；**只有一台机器时用单机规程（第 10.7 节：k6 容器限核 + JVM 限堆 + 结论分级）**——裸跑 k6 与应用抢 CPU，P99 失真。
- **负载模型**：常态基线用 `constant-arrival-rate`（`-e RATE=N`，固定迭代/秒），同样的 QPS 只需远少于 `ramping-vus` 的 VU 数，压测机开销小且结果可复现；容量拐点才用 `ramping-vus`。
- **压测机侧采样**：每个阶段同时跑 `collect_metrics.sh`（SUT 侧）与 `loadgen_metrics.sh`（压测机侧），输出 `results/metrics/loadgen-*.tsv`。
- **判定规则**：压测机 CPU > 80% 或 `http_req_blocked` 飙升时，测量无效——先加压测机资源再复测，不得判定为 SUT 瓶颈（见第 10 章交叉验证）。
- 压测前确认应用与中间件均为**独立进程**（`docker compose up -d` 后 `docker stats` 观察空闲基线）。

## 3. 指标定义

| 指标 | 口径 | 采集方式 |
|---|---|---|
| QPS（请求吞吐） | 每秒 HTTP 请求数，按 `name` tag 分组 | k6 `http_reqs` |
| TPS（业务吞吐） | 每秒**有效业务变更**（如 like 返回 `changed=true` 的次数、follow 返回 `true` 的次数） | k6 自定义 Counter（`counter.effective_writes` 等） |
| 延迟 | P50 / P95 / P99（ms） | k6 `http_req_duration` |
| 错误率 | `http_req_failed` 占比 | k6 |
| 消费积压 | Kafka consumer lag、RocketMQ 堆积 | `kafka-consumer-groups.sh` / `mqadmin` |
| 压测机水位 | 压测机 CPU/内存/网络/TCP 连接/FD（判定测量是否失真） | `loadgen_metrics.sh` → `results/metrics/loadgen-*.tsv` |
| Redis 水位 | ops/s、connected_clients、keyspace、`redis-cli --latency` | `collect_metrics.sh` |
| MySQL 水位 | Threads_connected、Queries 增量、慢查询 | `collect_metrics.sh` |
| 进程水位 | 应用/中间件 CPU、内存 | `docker stats` |
| 定时任务副作用 | 通知桶 KEYS 扫描耗时、聚合桶刷写、对账扫描 | 长稳阶段观测 Redis 阻塞事件 + 应用日志 |

**判定标准**：常态 = 错误率 < 0.5% 且 P99 稳定；高压拐点 = QPS 不再随 VU 增长，或 P99 跳升 > 2 倍基线，或错误率 > 1%。

## 4. 数据准备

所有种子脚本幂等（重复执行前先 `TRUNCATE` 相关表，见 6.1）。

| 数据 | 脚本 | 默认规模 | 说明 |
|---|---|---|---|
| 用户 + 钱包 | `seed_users.sql` | 1000 用户，ID 1000000 起 | 密码统一 `Loadtest@123`（BCrypt 哈希内嵌），手机号 `139` + 8 位序号；钱包余额 100 万 |
| 帖子 | `seed_posts.sql` | 500 篇 published，ID 2000000 起 | 作者轮转，第一篇为热帖（ID = POST_ID_BASE+1）；`publish_time` 倒序 |
| 关注关系 | `seed_follow_graph.sql` | 每用户关注 20 人 | 可选大V（≥10000 粉，fanout 场景；需先扩用户池到 ≥11000） |
| Cassandra | `gen_seed_cassandra.mjs` | 正文文本 + inbox + author_feed | 正文文本必须灌（否则详情读会回源外部 URL）；inbox 仅关注 Feed 场景需要 |
| Redis 预热 | `warm_sds.sh` | 计数 SDS + 用户计数 | 可选：预热避免读基线被「SDS 缺失→重建」污染；**想专门压重建风暴则跳过** |
| ES | 应用自回填 | — | 启动应用时索引为空会自动从 MySQL 回填（`SearchIndexInitializer`）；灌完帖子后重启应用一次 |
| 推广 | `seed_promotion.sql` | 1 活动 + 1 OPEN 窗口 | 竞价场景需要（`PROMOTION_BPRIME_ENABLED=true`） |

> 为什么种子用户走 SQL 直插：注册验证码是随机数且只进服务端日志（`LoggingCodeSender`），自动化无法获取。直插 BCrypt 哈希后走**密码登录**。

### 4.1 数据合规性与校验

**合规定义**：种子数据必须满足系统约束（唯一键、外键、格式正则、长度、状态机合法值、非负余额），否则压测时接口报错或数据静默丢失，测量结果不可信。`seed/*.sql` 与 schema（`db/schema.sql`）逐项对照设计：

| 约束来源 | 种子保证 |
|---|---|
| `users` 唯一键 phone/email、`^1\d{10}$`、邮箱正则 | 手机号 `139`+8 位序号（11 位）、`lt{i}@loadtest.local`（RFC 2606 保留域） |
| 密码登录依赖 | BCrypt 哈希（`gen_password_hash.mjs` 生成，密码 `Loadtest@123`） |
| `know_posts` 外键 creator_id、VARCHAR(50/256)、status/visible 枚举 | 作者取自种子用户、描述 ≤50 字符、状态 published/public |
| `following/follower` 唯一键、无自关注（业务层**不拦截**自关注） | 轮转公式 `j < USER_N` 保证无自关注；大V块显式排除大V自己 |
| `wallet_account` 非负 CHECK | 余额固定 1,000,000 |
| Cassandra 与 MySQL 一致性 | `gen_seed_cassandra.mjs` 与 `seed_follow_graph.sql` 共用同一轮转公式（**改公式必须两处同改**） |
| SDS 结构 | `warm_sds.sh` 写入恰好 20 字节（5 段 × 4 字节），避免误触发重建 |

**自动化校验**（新增，灌数后必跑）：

```bash
./run.sh verify     # 执行 seed/verify_seed.sql，输出 12 组检查
```

检查项：自关注、关注/钱包/帖子孤儿外键、非法 status/visible、负余额、字段长度越界、手机号/邮箱格式、缺密码哈希、sha256 长度、大V粉丝块越界、推广种子存在性。**所有 `violations` 必须 = 0**；`actual` 列人工核对（seeded-users = USER_N，promotion 竞价场景 = 1/1）。

**参数边界**（`run.sh seed` 已前置校验，违规直接退出）：

| 参数 | 约束 | 原因 |
|---|---|---|
| `USER_N` | ≥ 2 | 单用户必然自关注 |
| `FOLLOW_PER_USER` | < `USER_N` | 轮转公式 `(i+j-1)%N+1 == i ⟺ j ≡ 0 (mod N)` |
| `LARGE_FOLLOWER_N` | ≤ `USER_N - 1` | 大V粉丝必须落在用户池内且排除大V自己 |

**PII/隐私合规**：种子数据全部为合成值——手机号 `139` 号段序号、邮箱 `.local` 保留域（公网不可解析），不指向任何真实个人；注册/登录验证码仅打印到服务端日志（`LoggingCodeSender`），不触发真实短信/邮件。压测环境严禁使用真实用户数据。

## 5. 场景设计

所有脚本统一参数：`VUS`（峰值 VU）、`HOLD`（持压时长）、`RAMP`（爬升）、`P95`（阈值）；`RATE=N` 切换为 constant-arrival-rate（固定 N 次迭代/秒，常态基线首选，压测机开销小，见第 10 章）。示例：

```bash
k6 run -e BASE_URL=http://localhost:8080 -e VUS=500 -e HOLD=5m scripts/counter.js        # 容量测试：爬升到 500 VU 找拐点
k6 run -e BASE_URL=http://localhost:8080 -e RATE=200 -e VUS=400 -e HOLD=5m scripts/mixed.js  # 负载测试：固定 200 iter/s
```

### S1 auth — `scripts/auth.js`
- 内容：登录 50% / `/me` 40% / 刷新令牌 10%（token 15 分钟过期，脚本自动重登）。
- 断言：登录 200 且响应含 `token.accessToken`。
- 预期瓶颈：无单点；顺带测 RS256 每请求验签的 CPU 占比。

### S2 Feed 读 — `scripts/feed.js`（P0，最优先）
- 内容：公共 Feed（30% 匿名 / 70% 登录）50%、关注 Feed 25%（30% 概率带 cursor 翻页）、我的 Feed 15%、详情 10%。
- 断言：200 + `items` 数组 + `hasMore` 布尔。
- 预期瓶颈（代码实证）：
  - 关注 Feed 每页对每条目**同步串行 MySQL 点查**（`FollowFeedServiceImpl.mergeVisiblePage`）；
  - 关注 Feed **只有首页默认尺寸命中缓存**，翻页直读 Cassandra；
  - 关注 N 个大V → N 次作者头读取（Redis 未命中时单飞回源）；
  - 公共 Feed 未命中时一次填充写 N 个 item key + N 个反向索引 + 页索引；
  - 分布式单飞在 Redis 高延迟下的行为（见 S11）。

### S3 计数写读 — `scripts/counter.js`（P0）
- 内容：like/unlike/fav/unfav（50% 打热帖 `HOT_POST_ID`，50% 随机帖）+ 计数读 `GET /api/v1/counter/{etype}/{eid}?metrics=like,fav`。
- 断言：200 + `changed`/`liked` 字段存在；自定义计数 `counter.effective_writes` 统计 `changed=true`（**有效写 TPS**）。
- 预期瓶颈：热帖同分片位图单 key Lua 串行；Kafka 聚合桶膨胀；SDS 缺失触发重建（限速 3 次/10s + 单飞，压并发缺失时的行为）。

### S4 评论 — `scripts/comment.js`
- 内容：提交 40%（clientRequestId 唯一幂等）/ 评论列表 60%。
- 预期瓶颈：热帖评论 Kafka 消费吞吐（pending→落库）、评论列表深分页 + 每条文本 Cassandra 读。

### S5 关注关系 — `scripts/relation.js`
- 内容：follow 50%（**每 VU 至少隔 3 次迭代一次**，受令牌桶限流：容量 100、1 token/s/用户）、unfollow 10%、status 20%、following/counter 20%。
- 断言：follow 响应体 `=== true` 才算成功；`false` 计入 `relation.rate_limited` tag（限流不报错，返回 200+false）。
- 预期瓶颈：follow 写事务 + outbox；令牌桶限流是否误伤。

### S6 搜索 — `scripts/search.js`
- 内容：搜索 60%（热词/随机词，30% 概率带 `after` 深翻页）/ 联想 40%。
- 预期瓶颈：ES 单节点 QPS、function_score 加权查询成本、completion suggest 热前缀。

### S7 钱包 — `scripts/wallet.js`
- 内容：余额 / 流水 / 内容奖励配置。
- 预期瓶颈：`SELECT ... FOR UPDATE` 同账户串行（推广收单 HOLD 会打到钱包行锁，竞价场景联动）。

### S8 推广竞价 B' — `scripts/promotion.js`（P0，需 RocketMQ + bprime）
- 内容：出价提交 60%（全部打同一 campaign/窗口，构造收单竞争）/ 快照 20% / 活跃位 10% / 建活动 10%。
- 断言：200 + `commandId` 非空。
- 预期瓶颈：`promotion:auction:{id}:ranking` ZSET 与 campaign Hash 单窗口热写；RocketMQ 顺序消费吞吐；wallet HOLD 行锁。

### S9 混合用户旅程 — `scripts/mixed.js`（常态基线主场景）
- 内容：每迭代 = 1 次 Feed 首页 + 按概率：详情/点赞/计数读/评论列表/评论提交/搜索联想/关注/我的 Feed；随机 think-time 0.2~1s。
- 用途：**常态指标（阶段 B）与高压指标（阶段 C）都以此为准**，反映真实用户混合负载下各模块互相竞争资源的行为。

### S10 长稳 — `scripts/soak.js`
- 内容：constant-vus（默认 300 VU）2 小时混合旅程；阈值 P95 < 1000ms、错误率 < 1%。
- 观测：通知桶 KEYS 扫描（30s 周期）、计数聚合桶（1s 刷写）、`feed:public:pages` 与反向索引键空间增长、对账扫描（5min 周期）是否随运行时间劣化。

### S11 chaos-lite（故障注入，无脚本，手工执行）
| 注入 | 方法 | 验证点 |
|---|---|---|
| Redis 延迟/阻塞 | `redis-cli --latency` 观察；`tc netem` 或停容器 10s | 单飞心跳超时→误接管→恢复；SDS 重建锁；KEYS 扫描阻塞 |
| 正文 URL 挂起 | 将种子帖 `content_url` 指向黑洞地址（如 `http://10.255.255.1:81`） | `PublishManagerImpl` 用 `new RestTemplate()`（**无超时**），验证发布线程池是否被占满 |
| Kafka 停 | 停 kafka 容器 | 计数聚合桶滞留、通知桶滞留、位点不提交的恢复 |
| ES 停 | 停 es 容器 | 搜索接口错误行为、`SearchIndexService` 降级 |

## 6. 执行规程

### 6.0 前置
```bash
docker compose up -d                      # 全栈
# 可选: 大V/fanout 场景时扩用户池
```

### 6.1 灌数据（`./run.sh seed`）
```bash
cd loadtest
./run.sh seed            # 依次执行: users → posts → follow_graph → promotion → cassandra → redis 预热
docker compose restart app(如有)  # 触发 ES 索引自回填
# 验证: k6 run -e VUS=1 -e HOLD=1m scripts/mixed.js  冒烟通过后开始正式压测
```
> seed 默认**幂等**：脚本内先清空受影响表（见各 SQL 头部注释）。重复灌数需显式 `./run.sh seed --force`（先 TRUNCATE 再插）。

### 6.2 分级加压（阶段 A：单链路基准）
对 S1~S8 每个脚本，按 `VUS = 100 → 300 → 600 → 1000` 逐级加压，每级 `HOLD=4m`：

```bash
./run.sh baseline        # 内部循环: for script in auth feed counter comment relation search wallet promotion; for vus in 100 300 600 1000
```
每级记录：QPS、TPS（业务）、P50/P95/P99、错误率、Redis ops、MySQL 连接、消费积压 → 填第 7 节模板。

**拐点判定**：QPS 不再随 VU 上升 / P99 跳升 / 错误率 > 1% → 该级为容量上限。

### 6.3 阶段 B/C：混合常态与高压
```bash
./run.sh mixed           # B: VUS=300 HOLD=30m → 常态基线
```

## 9. 注意事项与坑（实测结论）

1. **follow 有限流**：令牌桶 容量 100 / 1 token/s/用户，超限返回 HTTP 200 + body `false`（不是 4xx）。relation 脚本按 VU 间隔 follow，并单独 tag `relation.rate_limited`。
2. **like 幂等**：同用户同实体重复 like 返回 `changed=false`，不产事件。计数压测看 `counter.effective_writes`（有效写 TPS），别只看请求数。
3. **验证码进日志**：新用户只能 SQL 直插 + 密码登录；密码策略 = 最小长度（配置默认）+ 必须含字母和数字，种子密码 `Loadtest@123` 满足。
4. **token 15 分钟过期**：脚本 401 时自动重登一次；长稳场景由 `ensureLogin` 按 `expiresAt` 提前刷新。
5. **SDS 缺失触发重建**：计数读基线建议先 `warm_sds.sh`；想测重建风暴（P0 关注点）则跳过预热并观察限速/单飞是否挡住。
6. **详情正文回源**：Cassandra 无正文文本时详情会回源 `content_url`（外部 URL），必须灌 `post_text_by_post_id`，否则详情压测打到外网。
7. **搜索数据**：先灌帖子再重启应用触发 ES 自回填；搜索场景前确认 `GET :9200/zhiguang_content_index/_count` > 0。
8. **竞价场景**：需 `PROMOTION_BPRIME_ENABLED=true` 且 RocketMQ 正常；收单窗口必须 OPEN（种子窗口 50 分钟有效，超时重灌）。
9. **Windows**：`run.sh`/`collect_metrics.sh`/`loadgen_metrics.sh` 为 bash 脚本，需 Git Bash 或 WSL；k6 从 https://k6.io/docs/getting-started/installation/ 安装。

## 10. 压测机资源保障与瓶颈判定（确保 k6 消耗不污染测量）

### 10.1 问题本质

k6 是 Go 进程，但 VU 脚本跑在 goja（纯 Go 的 JS 解释器）里：JSON 解析（`res.json()`）、断言、uuid、状态对象都消耗 CPU。**当压测机与应用同机时，k6 与应用抢 CPU/内存/网络栈，P99 与拐点都会失真**——测出来的可能是"k6 抢不过 JVM"而不是系统真实容量。回环网络的额外损耗很小（微秒级），同机的真正问题是资源竞争。

### 10.2 架构隔离（第一层）

| 阶段 | 要求 |
|---|---|
| 冒烟（VUS ≤ 50） | 允许同机回环 |
| 单链路基准 / 常态基线 / 高压拐点 | 首选**压测机与 SUT 物理分离**；只有一台机器 → 按 10.7 单机规程（k6 容器 `--cpus` 限核 + JVM 限堆），结论按"定位可信、绝对值保守"分级 |
| 长稳 soak | 同上；单机模式下 soak 建议 `RATE` 控制迭代速率而非大 VU（见 10.7 步骤 3） |

经验配比：脚本含 JSON 断言时，**每 1000 VU 约 0.5~1 核 + 1~2 GB 内存**（本项目单链路最多 1000 VU，4 核压测机足够；若后续加到 5000+ VU 或全用 `ramping-vus`，按此扩）。

### 10.3 负载模型省资源（第二层）

- **常态基线/可复现负载：`constant-arrival-rate`**（`-e RATE=N`，N 次迭代/秒）。同样的目标 QPS 下 VU 数可减少一个数量级：k6 只为维持速率分配必要 VU，压测机 CPU、TCP 连接、内存占用全部下降，且负载形态是"固定 QPS"而非"固定并发"，更接近业务语义。
- **容量拐点：`ramping-vus`**（默认）。找"系统在 N 并发下 QPS 到顶"的场景，此时 VU 数本身就是负载单位，无法替代。
- 两者结合：先 `ramping-vus` 找到拐点并发数，再在拐点前用 `RATE` 复测确认基线 QPS 与 P99。
- 脚本侧减负：只在断言处 `res.json()`（本项目已如此）；k6 默认 keep-alive 复用连接，不要人为禁用；不要开 `console.log` 风暴（`common.js` 仅在登录失败时输出）。

### 10.4 压测机侧检测（第三层）

每个阶段 run.sh 自动同时启动两个采样器：

```bash
./collect_metrics.sh  results/metrics/sut-<phase>.tsv      # SUT 侧：Redis/MySQL/Kafka/ES/应用健康
./loadgen_metrics.sh  results/metrics/loadgen-<phase>.tsv  # 压测机侧：CPU/内存/网络/TCP/FD
```

k6 侧判据（看 `results/*.log` 与 JSON 指标）：

| 信号 | 含义 |
|---|---|
| `http_req_blocked` 飙升（> 10ms） | 压测机建连困难：端口/TIME_WAIT 耗尽或网络栈饱和 |
| `http_req_failed` 中 connection reset / timeout 集中 | 先查压测机，再查 SUT |
| 实际 `iterations` 速率低于 `RATE` 设定 | 压测机 VU 饥饿（CPU 满） |
| `loadgen-*.tsv` 的 cpu_pct > 80 | 压测机先于 SUT 到顶，测量无效 |
| `file_nr` 接近系统上限（`/proc/sys/fs/file-nr`） | FD 耗尽 |

### 10.5 拐点交叉验证（第四层）

QPS 平台期出现时（QPS 不再随 VU 增长），按序排查：

1. 看 `loadgen-*.tsv`：压测机 CPU > 80%？→ 加压测机资源（加核/减 VU/换 arrival-rate）后**重测**，平台期消失则证明瓶颈在压测机。
2. 压测机正常 → 看 SUT 侧 `sut-*.tsv`：哪个组件先到顶（Redis ops 峰值 / MySQL 连接打满 10 / Kafka lag 上涨 / 应用 CPU 满）→ 该组件即瓶颈。
3. 用 `RATE` 以拐点前 80% 的 QPS 复测一轮：若 P99 明显低于拐点轮，说明平台期是真实容量上限而非偶发抖动。

### 10.6 每轮压测前的空载基线

正式压测前跑一次 1 分钟空载采样：

```bash
SAMPLE_INTERVAL=5 SAMPLE_DURATION=60 ./loadgen_metrics.sh results/metrics/loadgen-idle.tsv
```

压测机空闲 CPU 应 < 10%；SUT 侧 `docker stats` 各组件空闲水位与负载轮对比，作为"增量归属"的基准。

### 10.7 只有一台机器：单机压测规程

单机的本质问题：k6 与 JVM 抢同一份 CPU/内存/网络栈，竞争**可缓解、不可消除**。因此结论分级：

> **瓶颈定位（哪条链路差、哪个组件先到顶）在单机依然可信**——所有场景在同一竞争条件下测，横向对比成立；
> **绝对容量数字（QPS/P99 绝对值）是保守值**（k6 抢不过 JVM 时 SUT 显得更慢），对外宣称前需双机复测。

#### 步骤 1：k6 容器化限核（首选，一行开启）

```bash
# run.sh 已内置容器模式：k6 在容器里跑，默认限 2 核 + 1GB，BASE_URL 自动切 host.docker.internal
K6_DOCKER=1 ./run.sh baseline

# 收紧配额把 CPU 让给应用（应用侧至少留 4 核）
K6_CPUS=1 K6_MEM=512m K6_DOCKER=1 ./run.sh mixed
```

原理：Linux 容器 cgroup 配额（Docker Desktop 同样生效）把 k6 钉死在 ≤2 核内，无论脚本多能吃 CPU 都抢不过宿主 JVM；`loadgen-*.tsv` 的 cpu_pct 从此反映的是"k6 被限额后的占用"，不再与 JVM 直接竞争。

#### 步骤 2：JVM 限堆（防内存竞争 GC 抖动）

```bash
# mvn 启动
MAVEN_OPTS="-Xmx2g -XX:+UseG1GC" mvn spring-boot:run
# IDE 启动：VM options 填 -Xmx2g -XX:+UseG1GC
```

机器内存紧张时，k6 换页/JVM 换页会造成 P99 尖刺，限堆后双方都不触碰 swap。

#### 步骤 3：负载阶梯法（单机专用加压节奏）

```bash
# 常态基线：从低 RATE 起步，逐级确认 loadgen CPU < 50% 才升
k6_run run -e RATE=50  -e VUS=100 -e HOLD=2m scripts/mixed.js
k6_run run -e RATE=100 -e VUS=200 -e HOLD=2m scripts/mixed.js
k6_run run -e RATE=200 -e VUS=400 -e HOLD=2m scripts/mixed.js   # 到顶：loadgen CPU 接近 50% 或 SUT 先到顶

# 容量拐点：VUS 封顶 500（单机不建议更高），每级观察：
#   QPS 不再随 VU 增长 && loadgen cpu_pct < 80%  → 这是 SUT 真实拐点（保守值）
#   loadgen cpu_pct > 80%                          → k6 饱和，本级结论无效，降低 VUS 或收紧脚本
K6_DOCKER=1 BASELINE_SCRIPTS="feed counter" VUS_LEVELS="100 300 500" ./run.sh baseline
```

#### 步骤 4：同负载翻倍校准（单机判 k6 是否饱和）

同一 RATE 下把 `VUS` 翻倍重跑：若 QPS/P99 几乎不变且 loadgen CPU 显著上升 → 之前的数据未被 k6 饱和影响（VU 数富余）；若 QPS 上升 → 之前的负载被 k6 掐住了，需提高配额或降负载。

#### 步骤 5：Windows 亲和（可选，效果与容器限额重叠）

容器 `--cpus` 已够用；若不想用容器，可用 PowerShell 把 k6 钉到固定核：

```powershell
Start-Process k6.exe -ArgumentList 'run','-e','VUS=300','scripts/feed.js' -Affinity 0x3   # 只用核 0-1
```

#### 单机结果标注

结果模板（第 7 节）加一列 `环境`，填 `单机容器限核` 或 `单机直跑`；报告中所有绝对 QPS/P99 前标注"单机保守值"，横向对比结论（瓶颈位置）不标注。

#### 何时必须双机

需要对外交付容量数字（上线评审、SLA 承诺）时，单机数据不能作为依据——此时最低成本的方案是借一台按量付费云主机跑 k6（SUT 保持本机不动），`BASE_URL` 指向本机公网/内网地址即可，脚本零改动。
